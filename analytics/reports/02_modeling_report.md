## Task 7 — stratified train/test split (done first)

Class balance in the full dataset: not-survived (0) = **549**, survived (1) = **342** → survival rate **0.3838**.

Split: train **(712, 7)**, test **(179, 7)** (80/20, `stratify=y`, `random_state=42`).
Survival rate — train **0.3834**, test **0.3855**, full **0.3838**.

**Why stratification matters here.** The target is imbalanced at roughly 38%/62%. With a plain random 20% split, the minority class in the test set is sampled from only ~68 positives, so ordinary sampling noise can shift the test-set survival rate by several points. That moves recall and F1 — the metrics that matter most on the minority class — for reasons that have nothing to do with the model. Stratifying pins the class proportion in both splits to the population rate (train 0.3834 vs test 0.3855 above), so differences between models are attributable to the models. The split is performed **before** any preprocessing so that no imputation median, encoder category or scaler statistic is ever computed with test rows in view.

## Task 8 — preprocessing (fit on training data only)

Implemented as a `ColumnTransformer` inside a `Pipeline`:

| columns | steps |
|---|---|
| numeric `['age', 'sibsp', 'parch', 'fare']` | `SimpleImputer(strategy='median')` → `StandardScaler()` |
| categorical `['sex', 'embarked', 'pclass']` | `SimpleImputer(strategy='most_frequent')` → `OneHotEncoder(handle_unknown='ignore', drop='first')` |

Choices: median imputation for the numeric columns because `age` and `fare` are skewed and the median is robust to the long fare tail; most-frequent for `embarked`, which has only a couple of missing entries and three levels; one-hot with `drop='first'` to avoid the dummy trap for the linear models, and `handle_unknown='ignore'` so an unseen category at inference time degrades gracefully instead of raising.

This differs from Task 2's EDA-stage strategy, which dropped rows and dropped `deck`; here every step is a learned transformer so it can be fit on train and replayed on test. Because the transformers are declared inside the `Pipeline`, `pipe.fit(X_train, y_train)` is the only `fit` call in the script — `pipe.predict(X_test)` can only *transform*. The fit/transform separation is therefore structural, not a rule anyone has to remember.

## Task 11 — imbalance handling comparison

Class balance (full data): 0 = 549 (61.62%), 1 = 342 (38.38%) — roughly a 3:2 imbalance. Logistic Regression is retrained three ways on the same split.

```
                             precision  recall      f1
variant                                               
(a) baseline                    0.7797  0.6667  0.7188
(b) class_weight='balanced'     0.7391  0.7391  0.7391
(c) SMOTE (train fold only)     0.7397  0.7826  0.7606
```

| variant | precision | recall | F1 |
|---|---|---|---|
| (a) baseline | 0.7797 | 0.6667 | 0.7188 |
| (b) class_weight='balanced' | 0.7391 | 0.7391 | 0.7391 |
| (c) SMOTE (train fold only) | 0.7397 | 0.7826 | 0.7606 |

**Conclusion.** By F1 the winner is **(c) SMOTE (train fold only)** (0.7606); the highest recall comes from **(c) SMOTE (train fold only)** (0.7826). The pattern to read here is the trade: re-weighting and SMOTE both push the decision threshold toward the minority class, buying recall at the cost of precision. Whether that is an improvement depends on the cost asymmetry — for a survival-prediction model, missing a survivor (a false negative) is the expensive error, so the recall gain is worth a modest precision loss. The important caveat is that this dataset's imbalance is mild (~3:2); SMOTE earns its keep on far more skewed problems, and here it largely reproduces what the much cheaper `class_weight='balanced'` already achieves, while adding synthetic rows that must be confined to the training fold (enforced above by `imblearn.pipeline.Pipeline`, which runs the sampler during `fit` only).

## Task 13 — regression side-task: predicting `fare`

Target: `fare`. Predictors: passenger class, age, family counters, sex, port of embarkation and survival outcome. Same fit-on-train-only discipline.

- **MAE**: 19.1410
- **RMSE**: 31.1066
- **R²**: 0.3747
- **Adjusted R²**: 0.3414  (n = 179, p = 9 transformed predictors)

![residuals](figures/residual_plot.png)

Diagnostics: correlation between fitted value and |residual| = **+0.6530**; residual variance in the upper half of fitted values ÷ lower half = **12.51×**.

**Conclusion: yes, the residuals are heteroscedastic.** The spread of residuals is not constant across the fitted range — it fans out markedly at high predicted fares, confirmed by both diagnostics above. The mechanism is the one the EDA already flagged: `fare` is heavily right-skewed, so the model predicts a narrow band of mid-range fares well and misses the luxury tail badly, and those large misses all land at the right-hand end of the plot. This violates the constant-variance assumption of OLS, so the coefficient standard errors (and therefore any p-values or confidence intervals) are not trustworthy as reported — the point estimates remain unbiased. The standard remedies would be to model `log(fare)` instead, or to use heteroscedasticity-robust standard errors.

The modest R² (0.3747) is itself informative: fare is only partially explained by the recorded passenger attributes because cabin choice, group bookings and port-specific pricing are not in the dataset at all.

### Recommendation

I would deploy the **Random Forest**. It posts the best F1 on the held-out test set at **0.7481**, with accuracy 0.8156 and AUC 0.8329, against 0.7188 F1 / 0.8436 AUC for Logistic Regression and 0.6949 F1 / 0.8420 AUC for the single Decision Tree. F1 is the right headline metric because the classes are imbalanced (38.4% positive), so accuracy alone would reward a model that simply leaned toward the majority class, and AUC confirms the ranking holds across every decision threshold rather than at 0.5 only. The choice also matches what the EDA predicted: survival depends on threshold effects (the under-16 bonus) and non-monotonic ones (family size peaking at 2–4), which an ensemble of trees captures and a linear decision boundary cannot. The trade-off accepted is interpretability — if a stakeholder needs to read the rule rather than trust the score, the depth-4 Decision Tree is the honest fallback at a few points of F1.
